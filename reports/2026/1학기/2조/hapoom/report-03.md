# [제 3차 프로젝트 진행 보고서] 하품 홈페이지 웹 서비스 보안 취약점 분석

- **팀원:** (팀장) 20245035_강준수, (팀원) 20245039_김레빈, 20251790_김준수, 20252751_김홍균
- **활동 기간:** 2026. 06. 10. ~ 2026. 06. 23. (2주)

## 팀 전체 진행 현황

- **이번 회차 목표:**
  2차 보고서에서 공개 응답 기반으로 확인한 보안 설정 미흡 사항을 바탕으로, 제공받은 소스 코드와 테스트용 DB dump를 이용해 로컬 격리 환경에서 화이트박스 분석과 제한적 동적 재현을 수행한다. 운영 중인 `https://hapum.org/`에는 자동 스캔, 대량 요청, 파일 업로드 공격, 인증 우회 PoC를 수행하지 않고, 취약점 재현은 `127.0.0.1:18080` 로컬 환경에서만 진행한다.

- **현재 진행률:** 65%
  공개 설정 점검 단계에서 소스 코드 기반 정적 분석과 로컬 동적 검증 단계로 확장하였다. 주요 인증/인가, 파일 업로드, 저장형 XSS, 세션 쿠키, Redis, 정적 파일 공개 경로 이슈는 재현 가능성을 확인했으며, 다음 회차에는 패치 권장안 정리와 개선 후 재검증 체크리스트를 구체화할 예정이다.

- **주요 달성 사항:**
  - Spring Boot 소스 코드, MyBatis mapper, Thymeleaf template, Nginx 설정, 테스트용 DB dump를 확인하였다.
  - 운영 서버와 실제 SMTP를 사용하지 않고 로컬 격리 환경에서만 동적 검증을 진행하였다.
  - `SecurityConfig`에서 전체 요청이 `permitAll()`로 허용되고 CSRF가 비활성화되어 있음을 확인하였다.
  - 관리자 세션이 있는 상태에서 CSRF 토큰 없이 상태 변경 POST 요청이 처리되는 것을 로컬에서 확인하였다.
  - Summernote 이미지/비디오 업로드 및 삭제 API가 인터셉터 보호 범위 밖에 있어 비로그인 요청으로 접근 가능한 것을 확인하였다.
  - 관리자 입력 HTML이 `th:utext`로 출력되고 HTML 살균이 부족하여 저장형 XSS로 이어질 수 있음을 확인하였다.
  - `JSESSIONID`에 `HttpOnly`, `Secure`, `SameSite` 등 세션 쿠키 보호 속성이 부족한 점을 확인하였다.
  - 마이페이지 대관 및 프로그램 신청 삭제 POST 요청에서 소유자 검증 없이 리소스 id만으로 삭제가 수행될 수 있음을 확인하였다.
  - 신청서 docx 결과물이 `/result/**` 정적 리소스로 공개되고, 파일명이 순차적으로 추측 가능한 구조임을 확인하였다.
  - Redis 인증 설정이 비어 있고 이메일 인증번호가 평문 형태로 저장되는 구조를 확인하였다.
  - 설정 파일과 빌드 산출물에 DB 접속 정보와 메일 계정 비밀값이 포함될 수 있어 즉시 회전이 필요한 항목으로 분류하였다.

## 상세 점검 결과

### 1. 비밀정보 평문 노출

`application.properties`와 빌드 산출물에 DB 접속 정보, Redis 정보, 메일 계정 및 앱 비밀번호로 보이는 값이 포함되어 있었다. 소스 압축본이 외부 분석자에게 전달된 이상 해당 값은 이미 노출된 것으로 간주하고, 운영 비밀값을 즉시 폐기 및 재발급하는 것이 안전하다.

보고서에는 실제 비밀번호, 토큰, 계정 비밀값 원문을 기재하지 않는다. 개선안은 다음과 같다.

- 운영 DB 비밀번호, 메일 앱 비밀번호, Redis 비밀번호를 즉시 회전한다.
- `application.properties`에는 `${DB_PASSWORD}`, `${MAIL_PASSWORD}` 같은 환경변수 참조만 남긴다.
- 로컬 설정은 git에 포함하지 않는 `application-local.properties`로 분리한다.
- Git 기록과 빌드 산출물에 포함된 비밀값도 함께 점검한다.
- CI 단계에서 secret scanning을 적용한다.

### 2. Spring Security 무력화 및 CSRF 보호 부재

`SecurityConfig`에서 CSRF 보호가 비활성화되어 있고, 정적 리소스를 제외한 모든 요청도 `permitAll()`로 허용되어 있었다. 실제 접근 제어는 `AdminInterceptor`와 `UserInterceptor`에 의존하지만, 인터셉터 등록 범위는 `/admin/**`, `/main/mypage/**`로 제한되어 있다.

이 구조에서는 새로 추가된 민감 기능이나 `/writePost/**`, `/upload/**`, `/main/program/subs/**`, `/main/submitRental` 등 인터셉터 밖의 경로가 인증 없이 노출될 수 있다. 또한 관리자 로그인 상태에서 외부 페이지가 CSRF 토큰 없이 상태 변경 POST 요청을 유도할 경우 회원 상태 변경, 게시글 수정, 예약 처리 같은 동작이 수행될 수 있다.

개선안은 다음과 같다.

- `SecurityFilterChain`에서 `/admin/**`은 관리자 권한, `/main/mypage/**`와 업로드 관련 경로는 인증 사용자가 필요하도록 명시한다.
- CSRF 보호를 재활성화하고 Thymeleaf form 및 AJAX 요청에 CSRF 토큰을 포함한다.
- 인터셉터 중심 접근 제어를 Spring Security 권한 정책으로 이전한다.
- 꼭 필요한 API만 엔드포인트 단위로 CSRF 예외를 적용한다.

### 3. 파일 업로드 및 삭제 API 무인증

Summernote 이미지 업로드, 이미지 삭제, 비디오 임시 업로드, 비디오 임시 삭제 API가 `/admin/**` 또는 `/main/mypage/**` 하위가 아니어서 현재 인터셉터 보호 범위에 포함되지 않는다. 로컬 환경에서 비로그인 상태로 이미지 및 비디오 업로드 요청이 처리되고, 반환된 파일 경로가 공개 URL로 접근 가능한 것을 확인하였다.

주요 위험은 익명 사용자의 디스크 고갈, 악성 파일 호스팅, 저장형 XSS와의 결합이다. 개선안은 다음과 같다.

- 업로드 및 삭제 API에 인증 또는 관리자 권한을 적용한다.
- 이미지와 비디오 확장자 및 MIME type을 화이트리스트 방식으로 검증한다.
- 업로드 크기 제한을 기능별로 분리한다.
- 임시 파일은 TTL 기반으로 정리하고, 공개 URL 직접 접근이 필요한지 재검토한다.
- 삭제 API는 요청자가 업로드한 파일인지 또는 관리자 권한이 있는지 확인한다.

### 4. 저장형 XSS 및 세션 쿠키 보호 미흡

공지, 소식, 프로그램 상세 등 여러 템플릿에서 DB에 저장된 HTML을 `th:utext`로 출력한다. 저장 과정에서는 비디오 경로 이동 등 일부 후처리는 있지만, `<script>`나 이벤트 핸들러 기반 payload를 제거하는 공통 HTML 살균 로직은 확인되지 않았다.

또한 세션 쿠키 `HttpOnly` 설정이 꺼져 있어 XSS가 발생하면 `document.cookie`를 통한 세션 탈취 가능성이 커진다. 로그인 시 세션에 `User` 객체 전체가 저장되는 구조도 최소 정보 저장 원칙에 맞지 않는다.

개선안은 다음과 같다.

- 저장 전 Jsoup `Safelist` 등으로 허용 태그와 속성만 남기는 HTML 살균 로직을 공통 적용한다.
- 가능한 출력은 `th:text`를 우선 사용하고, 불가피하게 HTML을 허용하는 지점만 살균 후 `th:utext`를 사용한다.
- `server.servlet.session.cookie.http-only=true`, `secure=true`, `same-site=lax` 이상을 적용한다.
- 세션에는 비밀번호 해시가 포함된 전체 `User` 객체 대신 필요한 필드만 담은 세션 DTO를 저장한다.
- Nginx 또는 Spring Security에서 CSP 등 브라우저 보안 헤더를 추가한다.

### 5. 마이페이지 IDOR 및 임의 삭제 가능성

마이페이지 조회 화면은 URL의 사용자 id와 세션 사용자 id를 비교하는 검증 로직이 있으나, 대관 삭제와 프로그램 신청 삭제 POST 요청은 대상 리소스의 소유자 검증 없이 전달받은 id만으로 삭제를 수행한다. Mapper에서도 `user_id` 조건 없이 `id`만 기준으로 삭제한다.

로컬 테스트 DB에서 일반 사용자 세션으로 다른 사용자의 대관 예약 및 프로그램 신청 id를 지정했을 때 삭제가 수행되는 것을 확인하였다. 이는 서비스 방해와 데이터 무결성 훼손으로 이어질 수 있다.

개선안은 다음과 같다.

- 삭제 전 대상 리소스의 `user_id`와 세션 사용자 id가 일치하는지 확인한다.
- Mapper에도 `WHERE id = #{id} AND user_id = #{userId}` 조건을 추가하여 이중 방어한다.
- 모든 마이페이지 POST 요청에 동일한 소유권 검증 정책을 적용한다.
- 회원 탈퇴 등 계정 상태 변경 기능에서도 path variable id와 세션 사용자 id 비교 로직을 재점검한다.

### 6. 신청서 docx 결과물 공개 접근

프로그램 및 대관 신청 과정에서 생성되는 Word 문서가 `/doc/result` 경로에 저장되고, `WebConfig`에서 `/result/**` 정적 리소스로 매핑되어 있다. 파일명도 `program_{id}.docx`, `rental_{id}.docx`처럼 순차 id 기반으로 생성되어 추측 가능하다.

로컬 환경에서 비로그인 상태로 `/result/program_1.docx` 형태의 경로 접근 시 파일 다운로드가 가능한 것을 확인하였다. 신청서에는 이름, 전화번호, 소속 정보 등 개인정보가 포함될 수 있으므로 공개 정적 서빙 방식은 제거해야 한다.

개선안은 다음과 같다.

- `/result/**` 정적 리소스 핸들러를 제거한다.
- 인증과 소유권 검증이 포함된 다운로드 컨트롤러로 대체한다.
- 파일명에는 순차 id 대신 UUID 또는 별도 file token을 사용한다.
- 문서 저장 경로를 웹 공개 경로 밖으로 이동한다.
- 메일 첨부 후 서버 파일이 계속 필요하지 않다면 즉시 삭제하거나 TTL 정리 배치를 둔다.

### 7. Redis 인증번호 관리 미흡

Redis 비밀번호가 비어 있고, 회원가입 이메일 인증번호가 이메일 주소를 key로 하여 평문 저장되는 구조를 확인하였다. 로컬 환경에서는 Redis 접근 권한이 있는 사용자가 인증번호 값을 조회할 수 있었다. 추가로 인증번호 생성 값이 정적 필드에 저장되는 구조는 동시 요청 시 코드 혼선 가능성이 있다.

개선안은 다음과 같다.

- Redis `requirepass`를 설정하고 애플리케이션 설정과 동기화한다.
- Redis는 `bind 127.0.0.1`, `protected-mode yes` 등 내부 접근 제한을 적용한다.
- 인증번호 key는 `auth:signup:{email}`처럼 네임스페이스를 구분하고, 값은 평문 대신 해시 저장을 검토한다.
- 인증번호 검증 실패 횟수 제한과 재전송 제한을 둔다.
- 인증번호를 static 필드에 저장하지 않고 요청 단위 지역 변수로 처리한다.
- 난수 생성에는 `SecureRandom`을 사용한다.

## 이슈 및 해결 방안

- **문제 상황:**
  1. 운영 서버는 실제 이용자가 있는 서비스이므로, 자동화 스캔이나 공격성 PoC를 직접 수행할 경우 서비스 장애나 데이터 훼손 위험이 있다.
  2. 제공받은 소스와 테스트 DB에는 비밀정보 및 개인정보성 데이터가 포함될 가능성이 있어 보고서 작성 시 원문 값 노출을 피해야 한다.
  3. Spring Security 비활성화, CSRF 부재, 업로드 무인증, 저장형 XSS, IDOR, Redis 설정 미흡 등 여러 취약점이 구조적으로 연결되어 있어 단일 패치만으로는 충분하지 않다.
  4. 현재 재현은 로컬 격리 환경 기준이므로, 운영 반영 전에는 개발팀과 함께 영향 범위와 패치 우선순위를 조율해야 한다.

- **해결 현황:**
  운영 서비스에는 부하성 요청이나 공격성 PoC를 수행하지 않고, 로컬 환경에서만 취약점 재현 여부를 확인하였다. 보고서에는 실제 비밀번호, 이메일 인증번호, 개인정보 원문을 포함하지 않고 취약 구조와 개선 방향만 정리하였다. 패치 우선순위는 비밀정보 회전, Spring Security 및 CSRF 복구, 업로드 API 인증 적용, 세션 쿠키 보호 속성 적용, IDOR 소유권 검증, `/result/**` 공개 서빙 제거, Redis 인증 적용 순서로 정리하였다.

## 다음 회차 목표

- 노출된 운영 비밀값 회전 여부와 설정 파일 분리 방식을 확인한다.
- Spring Security 기반 권한 정책과 CSRF 토큰 적용 방안을 구체화한다.
- 업로드 API의 인증, 확장자/MIME 검증, 파일 크기 제한, 임시 파일 정리 정책을 패치 체크리스트로 작성한다.
- 저장형 XSS 방지를 위한 HTML 살균 정책과 CSP 적용 방안을 정리한다.
- 마이페이지 삭제성 POST 요청 전체에 소유권 검증이 적용되었는지 재검증한다.
- `/result/**` 정적 파일 공개 경로를 인증 다운로드 컨트롤러로 대체하는 방안을 검토한다.
- Redis 인증번호 저장 방식, 실패 횟수 제한, 재전송 제한을 점검한다.
- 최종 보고서에 포함할 취약점별 위험도, 재현 조건, 영향도, 개선안, 재검증 결과 형식을 확정한다.
