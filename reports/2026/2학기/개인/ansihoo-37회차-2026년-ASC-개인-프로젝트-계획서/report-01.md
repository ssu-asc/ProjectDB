| **프로젝트 분야** | 웹 해킹 / 취약점 분석 / AI 활용 보안|

## 프로젝트 개요

> LLM이 버그바운티의 어느 단계에서 실제로 도움이 되고 어디서 틀리는지 직접 측정한다. 취약점 목록이 공개된 로컬 실습 환경(OWASP Juice Shop, DVWA)에서 AI에게 소스코드 분석과 공격 후보 생성을 맡긴다. 그 결과를 정답 목록과 비교해 정확도(진짜 취약점 비율)와 놓친 취약점을 수치로 정리한다. 이 측정을 바탕으로 "AI가 후보를 만들고 → 사람이 재현해 검증하고 → 검증된 것만 신고"하는 워크플로를 만든다. 마지막으로 실제 공개 버그바운티 프로그램 하나의 스코프와 AI·자동화 정책을 분석하고, 허용 범위 안에서 이 워크플로를 적용해 본다.

## 기대 효과

- AI 보조 취약점 탐색의 강점과 한계를 감이 아닌 수치로 파악함
- 검증되지 않은 AI 신고서(AI slop) 문제를 피하는, 사람 검증 중심 워크플로를 확보함
- 웹 취약점 원리 이해와 신고서 작성 경험을 함께 쌓음

# 프로젝트 세부 계획서

## 1. 프로젝트 목적 (추진배경, 취지 등)

- AI 코딩 도구가 보급되면서 LLM으로 취약점을 찾으려는 시도가 크게 늘었다. 그 부작용으로 검증되지 않은 AI 신고서가 버그바운티 프로그램에 쏟아졌고, 오픈소스 프로젝트 curl은 이런 신고 때문에 버그바운티 운영을 중단하기도 했다. 일부 프로그램은 자동화 도구와 LLM 사용을 금지하거나 제한한다.
- 나는 사전 탐색 단계에서 AI와 자동화 도구로 공개 버그바운티 대상을 직접 훑어봤다. 사용한 도구는 GitHub Actions 정적 분석기 zizmor, 유출 시크릿 탐지기 trufflehog, 서브도메인 탈취 후보 탐색이었다. 약 50개 저장소와 4개 프로그램을 점검했다. 그 결과 시크릿 탐지에서만 2,133건의 "탐지"가 나왔지만 실제로 유효한 것은 0건이었고, 다른 방법도 모두 보상 대상 0건이었다. 그래서 다음 결론을 얻었다. AI와 자동화는 후보를 빠르게 만들지만, 그것이 진짜인지 판단하는 검증 능력이 없으면 결과가 0이다.
- 이 프로젝트의 목적은 두 가지다. ① AI가 어디까지 믿을 만한지 정답이 있는 환경에서 측정한다. ② 그 결과를 바탕으로 AI의 속도와 사람의 검증을 결합한 실전 워크플로를 만든다.

## 2. 프로젝트 세부내용

- 단계	기간(예상)	내용
1. 기초 학습	1~2주	Dreamhack Web Hacking Basics(SQLi, XSS, Access Control), HTTP 구조, Burp Suite 사용법. AI가 낸 결과를 판단하려면 원리를 먼저 알아야 하므로 이 단계를 맨 앞에 둠
2. 실습 환경 구축	3주	Docker로 Juice Shop·DVWA를 로컬에 구축하고, Juice Shop Score Board의 취약점 목록을 정답지로 정리
3. AI 탐색 실험	4~6주	① 소스코드 리뷰: AI에게 Juice Shop 소스를 주고 취약점과 위치(파일:라인) 찾기 ② 공격 후보 생성: 요청/응답을 주고 공격 입력값 제안받기 ③ 신고서 초안 작성. 각 결과를 직접 재현해 진짜 / 오탐 / 놓침으로 분류
4. 결과 분석	7주	유형별 정확도(precision, AI가 찾은 것 중 진짜 비율)와 탐지율(recall, 전체 정답 중 찾은 비율)을 계산함. "AI가 잘하는 것 / 자주 틀리는 것 / 사람이 꼭 확인해야 하는 것"을 정리
5. 워크플로 설계	8주	실험 결과를 바탕으로 AI 후보 생성 → 사람 재현 검증 → 근거(파일:라인, 실제 입력값) 첨부 → 신고서 체크리스트를 작성
6. 실제 프로그램 적용	9~10주	공개 버그바운티 프로그램 1개를 골라 스코프, 금지 행위, 세이프하버, AI·자동화 사용 정책을 분석함. 허용 범위 안에서 패시브 정찰과 수동 테스트에 워크플로를 적용하고, 결과(0건이어도)와 과정을 기록
7. 정리	마지막 주	실험 데이터, 워크플로, 가이드를 정리해 발표

원칙

스코프에 명시되지 않은 대상에는 트래픽을 보내지 않는다.
AI가 만든 결과는 직접 재현하기 전까지 "후보"로만 취급하며, 검증하지 않은 내용은 절대 신고하지 않는다.
AI 사용을 금지하는 프로그램에서는 AI를 쓰지 않는다.

## 3. 프로젝트 기대효과

- 데이터: "AI가 웹 취약점을 얼마나 정확히 찾는가"에 대한 직접 측정 결과(유형별 정확도와 탐지율)를 얻음
- 기술: 웹 취약점 원리, Burp Suite, AI를 보안 업무에 쓰는 법(프롬프트 설계, 결과 검증)을 익힘
- 윤리: 허가 범위와 AI 사용 정책을 확인하는 습관이 생기고, 신고서 품질 기준을 체득함
- 결과물: 재사용 가능한 검증 워크플로와 신고서 예시가 포트폴리오로 남음

## 4. 프로젝트 수행시 문제점 (내외부 요인 기술)

- 내부 요인 |
웹 분야 경험이 없음 → AI 결과를 판단할 수 있도록 기초 학습을 실험 전에 배치
AI 답을 그대로 믿는 확증 편향 → 모든 결과를 직접 재현해 분류하고, 정답지와 대조
- 외부 요인 | 
AI 출력이 실행할 때마다 달라질 수 있음 → 같은 입력을 여러 번 실행하고 프롬프트와 모델 버전을 기록 /
실습 환경의 취약점 정보가 이미 AI 학습 데이터에 포함됐을 수 있음(Juice Shop은 유명 프로젝트) → 결과 해석 시 한계로 명시하고, 가능하면 직접 만든 작은 취약 코드로 보조 실험 /
실제 서비스는 이미 많이 점검돼 입문자가 유효 취약점을 찾을 확률이 낮음(사전 탐색 결과 0건) → 성과 기준을 "보상"이 아니라 "측정 데이터 + 워크플로 + 규칙 내 적용 기록"으로 설정 /
프로그램별 AI·자동화 정책이 다르고 허가 범위를 잘못 해석하면 법적 문제(정보통신망법 등)가 생길 수 있음 → 정책을 문서로 확인한 범위에서만 진행

- 사전지식: HTTP 구조(요청/응답, 쿠키, 세션), HTML/JavaScript·SQL 기초, Python 기초, 정확도/탐지율 같은 기본 평가 지표 개념
- 보유 역량: C·Python 기본 문법, Dreamhack 어셈블리·시스템 해킹, 웹 해킹 로드맵 일부 수료, AI·자동화 도구(zizmor, trufflehog, subfinder)로 공개 대상을 사전 탐색한 경험

## 개인 수행 계획

- **주요 수행 항목:** 웹 기초 학습 → 실습 환경과 정답지 구축 → AI 탐색 실험(코드 리뷰 / 공격 후보 / 신고서 초안) → 정확도 분석 → 검증 워크플로 설계 → 실제 프로그램에 규칙 내 적용 → 정리
- **예상 산출물:** AI 탐색 실험 결과표(유형별 정확도·탐지율, 오탐 사례 분석) /
AI 보조 + 사람 검증 버그바운티 워크플로 체크리스트 /
검증된 취약점 기반 신고서 3건 이상 / 
대상 프로그램 스코프·AI 정책 분석 문서 /
- **검증 방법:** Juice Shop Score Board(공개 정답 목록)와 AI 결과를 대조해 정확도·탐지율을 계산 /
AI가 제시한 모든 후보를 직접 재현해, 재현된 것만 "진짜"로 인정 /
프롬프트와 모델 버전을 기록해 다른 사람이 같은 실험을 반복할 수 있게 함 /
