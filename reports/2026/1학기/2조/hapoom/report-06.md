# [제 6차 프로젝트 진행 보고서] 하품 홈페이지 웹 서비스 보안 취약점 분석

- **팀원:** (팀장) 20245035_강준수, (팀원) 20245039_김레빈, 20251790_김준수, 20252751_김홍균
- **활동 기간:** 2026. 07. 22. ~ 2026. 08. 04. (2주)

## 팀 전체 진행 현황

- **이번 회차 목표:**
  5차 보고서에서 로컬 기준으로 정리한 보안 패치와 검증 결과를 운영 반영 전 점검 항목으로 옮겨 정리한다. 이번 회차는 새로운 공격성 PoC를 늘리는 것보다, 패치가 실제 운영 환경으로 넘어갈 때 빠지면 안 되는 설정, migration, 자격 증명 회전, 재검증 흐름을 정리하는 데 초점을 둔다.

- **현재 진행률:** 98%
  코드 수준 취약점과 로컬 검증 항목은 대부분 정리된 상태. 다만 운영 서버에는 아직 직접 반영하지 않았고, 실제 프록시/TLS/메일/스토리지 환경에서의 배포 후 인증 DAST와 회귀 테스트는 남아 있다. 따라서 최종 확정 표현보다는 “운영 반영 전 준비 단계”로 구분한다.

- **주요 달성 사항:**
  - 5차 보고서의 패치 결과를 운영 반영 전 체크리스트로 재정리
  - IDOR, CSRF, 업로드, XSS, 이메일 인증 우회 항목의 운영 전 확인 기준 정리
  - 관리자 감사 로그 migration 적용 시 확인할 DB 변경 항목 정리
  - DB, Redis, 메일 자격 증명 회전 순서와 영향 범위 정리
  - 운영 환경변수, 신뢰 프록시, TLS, 메일, 스토리지 설정 재검증 항목 정리
  - 수정 전/후 비교 자료와 자동 검증 수치를 최종 보고서에 넣을 수 있는 형태로 정리
  - 운영 비밀값, 세션 값, 원본 개인정보를 보고서와 발표자료에 넣지 않는 기준 재확인

### 운영 반영 전 확인 항목

| 구분 | 확인 내용 | 현재 판단 |
|---|---|---|
| 관리자 감사 로그 | 운영 DB에 migration 적용 전 백업, rollback, 컬럼 타입 확인 | 배포 전 확인 필요 |
| Secret 회전 | DB, Redis, 메일 계정 비밀번호 교체 및 애플리케이션 환경변수 반영 | 운영 담당자 확인 필요 |
| 환경변수 | 로컬 설정과 운영 설정을 분리하고, 소스에 비밀값이 남지 않는지 확인 | 적용 방식 정리 |
| 신뢰 프록시 | 실제 Nginx/프록시 IP만 신뢰하도록 `X-Forwarded-*` 처리 범위 제한 | 운영망 기준 확인 필요 |
| TLS/쿠키 | `Secure`, `HttpOnly`, `SameSite` 속성이 HTTPS 운영 응답에서 보이는지 확인 | 배포 후 재검증 필요 |
| 메일 | 회원가입/비밀번호 재설정 메일이 실제 SMTP에서 정상 동작하는지 확인 | 배포 후 재검증 필요 |
| 스토리지 | 업로드 파일 저장 경로, 공개 URL, 임시 파일 정리 정책 확인 | 운영 경로 확인 필요 |

### 취약점별 마무리 상태

| 항목 | 로컬 패치 상태 | 남은 확인 |
|---|---|---|
| 회원가입 이메일 인증 우회 | hidden field 신뢰 제거 방향으로 정리 | Redis key, 만료시간, 재전송 제한 운영 확인 |
| CSRF | 상태 변경 요청 차단 기준 정리 | 운영 배포 후 주요 POST 403/정상 요청 재검증 |
| IDOR | 세션 사용자와 리소스 소유자 비교 기준 정리 | 실제 사용자 데이터 훼손 없이 테스트 계정으로 확인 |
| 파일 업로드 | 인증, 확장자/MIME/content 검증 기준 정리 | 운영 저장 경로와 파일 크기 제한 확인 |
| 저장형 XSS | sanitizer 및 CSP 적용 기준 정리 | 운영 CSP nonce와 HTML 출력 지점 재확인 |
| 세션 보안 | 로그인 후 세션 ID 교체, 계정 상태 변경 시 세션 무효화 기준 정리 | 실제 쿠키 속성과 세션 만료 흐름 확인 |
| Rate Limit | 로그인 및 인증 API 보호 기준 정리 | 운영 트래픽 기준 제한값 조정 |

### 최종 보고서에 넘길 자료

이번 회차에서는 최종 보고서에 바로 옮길 수 있도록 자료 묶음을 정리했다.

- 수정 전 취약 구조: 3차, 4차 보고서의 정적 분석 및 로컬 PoC 결과
- 수정 후 상태: 5차 보고서의 패치 적용 결과와 자동 검증 수치
- 검증 수치: 자동 테스트 95개, GET 라우트 45개, CSRF 없는 POST 64개, 정적 자산 81개, CSP 응답 44개
- 운영 미반영 항목: DB migration, Secret 회전, 환경변수, 프록시/TLS/메일/스토리지 재검증
- 발표 제외 정보: 운영 비밀값, 세션 값, DB dump의 원본 개인정보, 실제 사용자 식별값

### 남은 리스크

현재까지의 결과는 로컬 분석 랩 기준이다. 그래서 실제 운영 반영 전에는 다음 리스크를 따로 봐야 한다.

1. 운영 프록시와 애플리케이션이 HTTPS 여부를 다르게 인식할 가능성
2. CSRF 적용 후 기존 관리자/사용자 form 또는 AJAX 요청 일부가 누락될 가능성
3. 파일 업로드 제한 강화 후 정상 이미지, 영상 업로드 UX가 달라질 가능성
4. Redis, 메일, DB 자격 증명 회전 과정에서 서비스 설정이 엇갈릴 가능성
5. CSP 강화 후 기존 inline script나 외부 리소스 로딩이 깨질 가능성

## 이슈 및 해결 방안

- **문제 상황:**
  1. 5차 보고서에서 로컬 패치와 검증 수치는 정리됐지만, 운영 반영 전 조치가 여러 영역에 흩어져 있었다.
  2. 운영 서버에 바로 적용하지 않은 상태라, “취약점이 완전히 사라졌다”처럼 단정해서 쓰면 실제 배포 단계와 어긋날 수 있다.
  3. Secret 회전, DB migration, 프록시/TLS/메일/스토리지 설정은 코드만으로 끝나는 일이 아니라 운영자 확인이 필요하다.
  4. 최종 보고서에 넣을 자료가 3차, 4차, 5차 보고서에 나뉘어 있어 다시 묶어야 했다.

- **해결 현황:**
  이번 회차에서는 새 공격 테스트를 늘리기보다 운영 반영 전 확인표와 최종 보고서 재료를 정리. 로컬 기준으로 조치된 항목과 운영 배포 후 다시 봐야 할 항목을 분리했다. 운영 비밀값, 세션 값, 원본 개인정보는 계속 보고서/발표자료에서 제외하는 방향으로 유지.
