# [제 1차 개인 프로젝트 진행 보고서] ASC 개인 프로젝트 1회차

- **작성자:** 양진우 (team05_02)
- **활동 기간:** 2026. 10. 26. ~ 2026. 11. 01.
- **프로젝트 주제:** AI 기반 C/C++ 취약점 탐지 모델 구현 및 패치 전후 판별 성능 분석

## 프로젝트 진행 현황

- **이번 회차 목표:** 계획서의 1-2주차 목표인 보안 기초 학습과 취약점 사례 분석을 시작한다. C/C++의 포인터·배열·동적 메모리와 메모리 경계를 정리하고, 공개 취약점 2-3건의 발생 원인과 패치를 분석한다. 로컬 실습으로 메모리 오류와 수정 전후 동작 차이를 확인한다.
- **현재 진행률:** 약 15% (전체 8주 계획 대비 초기 자료 정리·사례 분석·기초 실습 산출물을 기준으로 한 추정치. 원본 취약점 재현, 데이터 구성, 모델 학습과 성능 평가는 후속 과제로 남아 있다.)
- **주요 달성 사항:**
  - 포인터·배열·동적 메모리와 힙 버퍼 오버플로, 이중 해제, 해제 후 사용의 차이를 정리한 기초 자료를 작성하였다.
  - curl의 공개 취약점 3건을 선정하고, 공식 보안 공지와 수정 커밋을 바탕으로 발생 조건과 패치 내용을 비교하였다.
  - 교육용 힙 버퍼 복사 예제를 작성하고, AddressSanitizer로 수정 전후의 동작을 검증하였다.
  - 후속 실험에서 사용할 데이터 분할 점검 항목과 패치 전후 코드 쌍 평가 기준을 초안으로 정리하였다.

## 수행 내역

- **수행 작업:**
  1. **메모리 취약점 기초 자료 작성**
     - AI 도구를 활용하여 포인터와 배열의 관계, 동적 메모리의 할당·해제, 버퍼 경계 및 객체 수명을 정리하였다.
     - 위험한 함수의 존재 여부만으로 판단하기보다 복사 길이, 입력 검사, 해제 시점과 호출 흐름을 함께 확인해야 한다는 분석 기준을 마련하였다.
  2. **공개 취약점 및 패치 분석**
     - CVE-2023-38545: SOCKS5 처리 과정에서 발생한 힙 버퍼 오버플로와, 과도하게 긴 호스트 이름을 오류로 처리하도록 바꾼 패치를 분석하였다.
     - CVE-2022-42915: HTTP 프록시 연결 실패 후 정리 과정에서 발생한 이중 해제와 프로토콜 포인터 복구·정리 경로 변경을 분석하였다.
     - CVE-2022-43552: 프록시 연결 거부 후 SMB/TELNET 종료 과정의 해제 후 사용과 구조체 수명 관리 변경을 분석하였다.
     - 세 사례의 유형, 발생 조건, 관련 파일, 수정 방향과 공식 출처를 사례 분석 자료에 기록하였다.
  3. **로컬 메모리 오류 실습 및 결과 수집**
     - AI 도구를 활용하여 16바이트 힙 버퍼에 데이터를 복사하는 C 예제와 실행·검증 스크립트를 작성하였다.
     - 길이 검사 유무로 수정 전후 버전을 구성하고, Windows의 MSVC 및 AddressSanitizer 환경에서 동일한 입력을 실행하였다.
     - 입력 길이는 1·15·16·17·32바이트로 구성하여 정상 범위, 경계값, 경계 초과 상황을 비교하였다.
     - 이 실습은 취약점의 기본 원리를 확인하는 축소 예제이며, 위 CVE의 curl 원본 환경 재현은 아직 완료하지 않았다.
  4. **후속 모델 실험 설계**
     - PrimeVul 공식 저장소의 데이터·평가 안내와 LLMxCPG의 초록을 확인하고, 데이터 중복·분할·문맥 확인 항목을 정리하였다.
     - 정밀도·재현율·F1과 함께, 취약 코드와 대응 수정 코드를 모두 맞힌 쌍의 비율을 평가 항목으로 설정하였다. 논문 전체 분석과 실제 데이터 확인은 다음 회차에 수행한다.

- **검증/확인 내용:**
  - 공개 사례 3건은 curl 공식 보안 공지와 공식 수정 커밋을 대조하였다.
  - 실습에서는 두 버전 모두 1·15·16바이트 입력을 정상 처리하였다. 취약 버전은 17·32바이트 입력에서 `heap-buffer-overflow`가 발생했고, 수정 버전은 복사 전에 해당 입력을 거부하였다.
  - 총 10개 실행 조건에서 예상 동작을 확인하고, 실행 환경·로그·소스 체크섬을 저장하였다. 이 결과는 실습 코드의 동작 확인이며 AI 모델의 탐지 성능 측정값은 아니다.

## 이슈 및 해결 방안

- **문제 상황:**
  - 공개 취약점은 입력 길이뿐 아니라 프로토콜 상태와 오류 처리 경로가 함께 작용하므로, 원본 환경을 재현하려면 버전·빌드 옵션·실행 조건을 추가로 구성해야 한다.
  - 계획서의 Linux 실습 환경과 달리 이번 검증은 Windows 환경에서 수행하였다.
  - 실제 데이터의 유형별 표본 수와 메타데이터를 확인하지 않아 최종 학습 대상과 모델 규모를 확정하지 못하였다.
- **해결 현황:**
  - 이번 회차에는 공식 패치 분석과 교육용 예제로 기초 검증을 진행하고, 원본 CVE 재현은 후속 작업으로 남겼다.
  - 설치된 MSVC의 AddressSanitizer로 실습을 실행하고 재실행 방법을 기록하였다. Linux에서의 동일 실습과 원본 환경 재현은 다음 회차에 확인한다.
  - 학습 전에 데이터 분할·중복·클래스 비율과 사용 가능한 GPU 자원을 먼저 점검하도록 실험 순서를 정리하였다.

## 다음 회차 목표

- 공개 취약점 1건의 원본 버전과 수정 버전을 로컬 환경에 구성하여 발생 조건, 오류 로그 및 패치 적용 후 결과를 비교한다.
- PrimeVul 논문의 문제 정의·데이터 구성·평가 방법을 정리하고, LLMxCPG의 문맥 활용 방법과 비교한다.
- PrimeVul 데이터를 확보하여 분할별·유형별 표본 수와 메타데이터를 확인하고, 실험할 메모리 취약점 유형 1~2개를 확정한다.
- 공식 분할을 기준으로 패치 전후 쌍과 중복 코드의 분할 간 누수 여부를 점검하고 전처리 기준을 기록한다.
- TF-IDF와 로지스틱 회귀 기반 분류 모델을 구현하여 소규모 데이터로 학습·평가 흐름을 확인한다.
- GPU 사용 환경을 확인하고 후속 코드 모델의 크기와 학습 설정을 정한다.
